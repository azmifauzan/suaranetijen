---
name: staging-image-redeploy
description: Use when redeploying suaranetijen to staging, or rolling a PHP or runtime security patch out to the staging app and its worker hosts.
category: deployment
---

Redeploy = gated build and push (docker-build-push-gate), then these steps on the staging host, in order.

Build from the committed tree, not the working copy: `git archive HEAD | tar -x -C <scratch-dir>`, then run `docker build` inside that directory. Uncommitted edits (for example an unrelated `resources/js/pages/*.vue` change) stay out of the image. Name them in the report as not deployed, and do not claim a live feature that depends on them.

0. Hold the deploy while a background data batch (enrich, import) is still running. Recreating the app container kills the batch mid-run. Wait for its FINISHED signal, then deploy.
1. Drain Horizon before recreating any worker container: `php artisan horizon:terminate` inside it, then recreate (see horizon-graceful-restart).
   Worker hosts: find each host's compose directory from the container label instead of guessing it: `docker inspect suaranetijen-horizon-worker --format '{{index .Config.Labels "com.docker.compose.project.working_dir"}}'`. Then, in that directory: `docker compose pull suaranetijen-horizon-worker` (check its exit code; never pipe it through `tail` under `set -e`, since the pipe hides a failed pull; confirm the compose `image:` line is `azmifauzan/suaranetijen:latest`, because a pin to a tag missing from the registry makes the pull fail and `--force-recreate` then silently restarts on the old local image), terminate, wait until the container reports running again, and `docker compose up -d --force-recreate --no-deps suaranetijen-horizon-worker`. Run this per host, one host at a time by default. When the user asks for parallel rollout (e.g. "paralel. ini kritikal"), run the hosts concurrently, but each host must still pass its own gate (pull exit 0, digest match, runtime version, Horizon running) before the rollout counts as done.
2. In `/home/dev/compose/suaranetijen`: `docker compose pull suaranetijen-app`, then `docker compose up -d --no-deps suaranetijen-app suaranetijen-scheduler suaranetijen-ssr`. Add other services only if their image changed. After a `--force-recreate`, check every service reports `Up`, not just `app`: a recreate can leave `suaranetijen-app` `Dead` and `suaranetijen-scheduler`/`suaranetijen-ssr` as `Created` (never started). Recovery: `docker rm -f` the Dead container and any leftover `<hash>_<name>` containers, then `docker compose up -d --no-deps suaranetijen-app suaranetijen-scheduler suaranetijen-ssr`, then re-run step 4 (nginx reload) and step 5 (cache flush). Root cause of the Dead state is not yet known; check host disk and Docker daemon if it recurs.
   `up -d` leaves a running container alone when its compose config is unchanged, even after a pull of the same `:latest` tag. A `Running` line in the output means the old image may still be serving. For each service whose digest changed, compare the container's image ID with the local image's ID on that same host, after the pull: `docker inspect -f '{{.Image}}' <container>` against `docker image inspect -f '{{.Id}}' azmifauzan/suaranetijen:latest`. Add `--force-recreate` if they differ. Image IDs are host-local (one worker reported `385be…` where the build host reported `0bacd…`, yet that worker's `RepoDigests[0]` matched the pushed digest), so never compare IDs across hosts. Prove a cross-host pull with `RepoDigests[0]` against the `digest: sha256:…` line that `docker push` printed.
3. Migrate: `docker exec suaranetijen-app php artisan migrate --force`.
4. Recreating the app container changes its IP, and nginx-proxy keeps the old one. Reload: `docker exec nginx-proxy nginx -t && docker exec nginx-proxy nginx -s reload`. Skipping this gives 502 on `/`.
5. After `suaranetijen-ssr` reports healthy, flush the public page cache: `docker exec suaranetijen-app php artisan tinker --execute "App\Http\Middleware\CachePublicPages::flush(); echo 'flushed';"`. A page requested while SSR was still starting is cached as a shell with no SSR HTML and is served as `x-page-cache: HIT` until flushed.
6. For a runtime or base-image bump (e.g. a PHP patch for a CVE), check the running version inside every container on every host with `docker exec <container> php -v` and compare it with the advisory's first fixed version. The image digest alone does not show that the process changed. Before pushing, check the built image itself with `docker run --rm --entrypoint php <image> -v`.
7. Verify public: `/` and `/up` return 200 on https://suaranetijen.id, then check the changed behaviour on one page, not just the status. Confirm the markup itself (`curl -s` + grep for the changed class or element), since a cached shell still returns 200.
6. Access: key auth to the staging host was denied in one session. Password auth with the staging credentials from local `.env` via sshpass worked. Read credentials from `.env` at run time. Never write them into a skill, command, log, or commit.
7. New data batches (enrichment, imports) are separate from redeploy. Verify them on a sample first (wikidata-entity-enrichment).
