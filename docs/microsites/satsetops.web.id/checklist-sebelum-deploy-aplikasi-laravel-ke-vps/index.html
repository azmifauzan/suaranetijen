Checklist Sebelum Deploy Aplikasi Laravel ke VPS

12 November 20262 menit baca

Deploy pertama sering berjalan lancar di komputer sendiri lalu bermasalah di server. Penyebabnya hampir selalu hal kecil yang terlewat. Gunakan daftar ini sebelum menekan tombol deploy, dan ulangi untuk setiap rilis penting.

Lingkungan dan versi

  • Versi PHP dan ekstensi yang dibutuhkan terpasang di server.
  • Versi Node untuk membangun aset, bila build dilakukan di server.
  • Composer terpasang dan composer install --no-dev --optimize-autoloader dijalankan.

Konfigurasi aplikasi

  • APP_ENV=production dan APP_DEBUG=false.
  • APP_KEY sudah di-generate dan disimpan di tempat aman, di luar server.
  • URL aplikasi, domain sesi, dan pengaturan email sudah sesuai produksi.
  • Kredensial database dan Redis memakai kata sandi kuat dan akses terbatas.

Database dan antrean

  • Migrasi dijalankan dengan php artisan migrate --force, setelah backup.
  • Worker antrean berjalan di bawah pengawas proses (Supervisor atau container terpisah) dan dimulai ulang tiap rilis.
  • Scheduler Laravel dipanggil lewat cron setiap menit.

Cache dan izin berkas

  • Jalankan config:cache, route:cache, dan view:cache.
  • Direktori storage dan bootstrap/cache dapat ditulis oleh pengguna web server.
  • Tautan penyimpanan publik dibuat dengan storage:link.

Keamanan dan jaringan

  • HTTPS aktif dan HTTP diarahkan ke HTTPS.
  • Berkas .env tidak bisa diakses dari web.
  • Firewall hanya membuka port yang perlu.

Rencana mundur

Simpan versi sebelumnya agar bisa kembali bila rilis bermasalah, dan tentukan siapa yang memutuskan rollback. Setelah deploy, buka halaman utama, lakukan satu alur penting seperti login, dan periksa log kesalahan beberapa menit pertama.

Pemeriksaan pascadeploy dalam lima menit

Setelah deploy selesai, jalankan pemeriksaan singkat yang sama setiap kali: buka halaman utama, login dengan akun uji, lakukan satu aksi yang menulis ke database, kirim satu email uji, dan lihat apakah pekerjaan antrean diproses. Periksa file log kesalahan untuk entri baru. Bila semua bersih, catat nomor versi rilis dan waktunya.

Siapkan juga halaman pemeliharaan yang bisa diaktifkan dengan satu perintah bila rilis membutuhkan waktu. Dan jangan lupa membersihkan cache setelah perubahan konfigurasi. Banyak masalah "sudah diperbaiki tetapi tidak berubah" hanya berasal dari cache lama yang belum dibuang. Daftar ini bisa disalin ke repositori sebagai berkas pedoman deploy untuk tim.

Pertanyaan yang sering muncul

Perlukah menjalankan composer install di server?

Bergantung alurmu. Banyak tim membangun image atau artefak di tempat lain lalu mengirimnya ke server.

Mengapa APP_DEBUG harus false?

Mode debug menampilkan detail kesalahan dan konfigurasi yang bisa membocorkan informasi sensitif.
