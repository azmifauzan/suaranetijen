Backup Database ke Penyimpanan Objek: Langkah dan Jadwal

12 November 20262 menit baca

Backup yang tersimpan di server yang sama dengan datanya bukan backup. Bila disk rusak atau akun provider diblokir, keduanya hilang bersamaan. Penyimpanan objek di luar server adalah tempat yang lebih aman, dan biayanya biasanya kecil untuk database ukuran proyek sampingan.

Langkah dasar

  1. Buat dump terkompresi. Untuk PostgreSQL gunakan pg_dump, untuk MySQL mysqldump, lalu kompres dengan gzip.
  2. Enkripsi berkas sebelum diunggah, terutama bila berisi data pengguna. Simpan kunci di tempat terpisah.
  3. Unggah ke penyimpanan objek yang kompatibel S3 dengan alat seperti rclone atau klien resmi penyedia.
  4. Beri nama berkas dengan tanggal, supaya mudah diurutkan dan dipulihkan.

Jadwalkan dengan cron

Bungkus langkah di atas dalam satu skrip, lalu jadwalkan harian di jam sepi. Tulis hasilnya ke log dan kirim pesan ke Telegram atau email bila skrip gagal. Backup yang gagal tanpa kamu ketahui sama dengan tidak ada backup.

Tentukan retensi

Simpan beberapa salinan harian, beberapa mingguan, dan beberapa bulanan. Contohnya tujuh harian, empat mingguan, dan tiga bulanan. Atur penghapusan otomatis untuk berkas yang lebih tua supaya biaya penyimpanan tidak membengkak.

Uji pemulihan secara berkala

Sebulan sekali, unduh satu backup, pulihkan ke database sementara di server lain, dan periksa isinya. Catat tanggal pengujian terakhir. Banyak orang baru menemukan backup rusak pada hari mereka membutuhkannya.

Jangan lupa data selain database

Berkas unggahan pengguna, konfigurasi, dan berkas rahasia aplikasi juga perlu disalin. Simpan konfigurasi dalam repositori pribadi dan rahasia di pengelola kata sandi, supaya pemulihan tidak bergantung pada ingatan.

Kerangka skrip backup sederhana

Skrip yang baik melakukan lima hal berurutan: membuat dump dengan nama bertanggal, mengompres, mengenkripsi, mengunggah, dan memverifikasi bahwa berkas di tujuan ada dan ukurannya wajar. Bila salah satu langkah gagal, skrip berhenti dan mengirim peringatan. Hapus berkas lokal setelah unggahan berhasil agar disk tidak penuh.

Catat juga waktu pemulihan yang kamu butuhkan. Uji sekali berapa lama proses unduh dan pulihkan untuk database berukuran sekarang, lalu tuliskan di dokumen darurat. Angka itu penting saat memutuskan apakah backup harian cukup atau perlu lebih sering. Bila memulihkan memakan waktu berjam-jam, pertimbangkan strategi yang lebih cepat seperti replika.

Pertanyaan yang sering muncul

Seberapa sering backup database dibuat?

Harian untuk kebanyakan proyek. Untuk data yang berubah cepat dan penting, pertimbangkan backup lebih sering atau arsip log transaksi.

Apakah backup harus dienkripsi?

Sangat dianjurkan, terutama bila berisi data pribadi pengguna atau disimpan di layanan pihak ketiga.
